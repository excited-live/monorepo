# Auth Migration Plan — WorkOS → Better Auth

> Status: Phase 1 merged (#99). Phases 2–4 delivered in feat/better-auth-webapp-and-biz.
> Scope: every app that touches auth today, verified in code on 2026-10-13.

## 1. Why

- **Public API tokens (prd-post-mlp.md §7).** The PRD requires scoped, revocable, audit-logged tokens with capability scopes (compute / plan:read / propose), "never session cookies". WorkOS has no user-facing scoped-key story; Better Auth's `apiKey` plugin is exactly this.
- **Native apps.** WorkOS AuthKit is a hosted, cookie-first service; the Tauri flow (external browser + custom scheme) fits a standard OAuth provider better than a hosted session vendor.
- **Custom domain.** AuthKit custom domain is a paid add-on. Better Auth sign-in lives on our own domain by definition.
- **Security debt today.** `apps/api` currently issues **unsigned** bearer tokens (`biz_tok_<base64 user json>`) and passes user PII (email, name) in deep-link URL query params. Both go away in this migration.
- **Cost of waiting.** The current WorkOS surface is small. After mobile + public API ship, the same migration touches far more code.

What we give up: a managed service (security patching is ours), the 1M-MAU free tier, and turnkey SSO. SSO is Phase 3 contact-sales per pricing.md and can be added back later as an OIDC/SAML connection without re-owning primary auth.

Existing infrastructure we build on:

- **Database already exists**: `apps/api/src/db` — Cloudflare D1 on Workers (`worker.ts`, binding `DB`) and `node:sqlite` on Node (`index.ts`), one migration ledger (`d1_migrations`), current migrations `0001_init.sql`, `0002_biz_store.sql`.
- **Env-gate pattern** (`authkitConfigured()` / `authRequired()`): unconfigured environments (PR previews, prelive, local) render signed-out. We keep this exact pattern.
- **Guard semantics** (issue #46): page-level gate + per-server-function `getAuth()` checks. Semantics preserved, provider swapped.

## 3. Target architecture

One auth package, one database, two mounts:

```
packages/auth            NEW — Better Auth instance factory + client + schema
  ├─ betterAuth() factory (same BETTER_AUTH_SECRET, same D1 tables)
  ├─ Kysely adapter, type "sqlite" (D1SqliteDialect on Workers, better-sqlite3/node:sqlite on Node)
  └─ authClient (createAuthClient) for UI

apps/webapp (Pages)      mount #1 — cookie sessions
  ├─ tanstackStartCookies() plugin (last in array)
  ├─ /api/auth/$ catch-all route (GET+POST → auth.handler)
  ├─ server fns via auth.api.getSession({ headers })
  └─ sign-in UI in our design system, bilingual { en, th }

apps/api (Workers)       mount #2 — tokens for native + public API
  ├─ bearer()      → Authorization: Bearer for mobile
  ├─ apiKey()      → scoped, revocable, expiring keys (compute / plan:read / propose)
  ├─ oidcProvider() → standard /oauth2/authorize + /oauth2/token for native apps & future third parties
  └─ no cookies; session rows shared with webapp mount
```

- Both apps bind the **same D1 database**; session/user rows are shared.
- One schema migration: `0003_auth.sql`, generated by the Better Auth CLI and applied by the existing `apps/api` migration machinery (Kysely SQLite/D1 is explicitly supported by Better Auth's programmatic migrations).
- Native flow (planned, superseded for biz-mobile — see Phase 4 note): browser → webapp sign-in page (our domain, our i18n) → OIDC authorize → `excitedlive://auth/callback?code=...` → Tauri deep link → code exchange at `/oauth2/token` → Bearer token in Tauri storage. No tokens or PII in redirect URLs.
- Delivered deviation (Prame's call): Excited.Biz mobile signs in IN-APP instead — email + password directly against the api's Better Auth bearer mount. No system browser, no deep link, no PII in URLs; the OAuth provider stays mounted for the future public API.

### Better Auth facts this relies on (verified against current docs)

- Official TanStack Start integration: `tanstackStartCookies()` plugin, `/api/auth/$` route pattern, `auth.api.getSession({ headers })` in server functions.
- Kysely adapter ships a `D1SqliteDialect`; D1 has no interactive transactions (batch API instead — our stores don't need them).
- `bearer()` and `apiKey()` plugins provide Bearer-token auth and scoped API keys respectively.
- `oidcProvider()` plugin turns the app into a standard OAuth2/OIDC issuer.
- Workers background tasks via `advanced.backgroundTasks.handler = waitUntil`.

## 4. Phases

### Phase 1 — Foundation (packages/auth)

- Add `packages/auth`: Better Auth factory, Kysely + sqlite driver wiring, shared config, typed client.
- Generate `0003_auth.sql` (user, session, account, verification + apiKey tables) into `apps/api`'s migration sequence.
- Secrets: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (names only in repo; values in repo secrets / local `.env` only). Update `.env.example` files.
- Decision needed: OQ-1 (prd-mlp.md) — email/password, Google social, or both. Recommendation: both from day one (subscription + 7-day trial needs self-serve signup).
- Email: Better Auth needs an email provider for verification/reset (WorkOS handled this free). Pick one (Resend recommended) or defer verification emails to Phase 5+.

**Implementation notes (Phase 1, done).** Facts that cost debugging time, for later phases:

- better-auth 1.7.x split plugins/adapters into scoped packages: `@better-auth/kysely-adapter`, `@better-auth/api-key`, `@better-auth/oauth-provider` (the old `oidcProvider` is removed). Core keeps `bearer` and `jwt`.
- `oauthProvider` **requires** the `jwt()` plugin (access-token signing) and both `loginPage` **and** `consentPage` options; without a `baseURL` its init throws `Invalid URL` — `createAuth` fail-fasts on that.
- `tanstackStartCookies()` must be the LAST plugin in the array (better-auth warns; its after-hooks own the framework cookie store). `createAuth` enforces token-plugins-first, cookie-last ordering.
- The OAuth provider metadata routes live under better-auth's base path: `/api/auth/.well-known/oauth-authorization-server` (200 verified in tests).
- The 1.7 `apikey` table stores the owner in `referenceId` (no `userId` column). `verifyApiKey` is a **serverOnly** endpoint (no HTTP route). `enableSessionForAPIKeys` stays **false** by design: API keys must not mock full user sessions — the api mount validates keys explicitly and maps scopes itself (Phase 3).
- Cookie-store session resolution cannot be unit-tested in bare Node: `tanstackStartCookies` hands cookies to the TanStack Start runtime. Phase 1 tests assert the set-cookie wire format; the cookie round-trip is proven in Phase 2 inside the webapp.
- Kysely 0.28's `QueryKind` is type-only; the D1 dialect matches node-kind strings (`"InsertQuery"` etc.). `Driver.beginTransaction` returns `Promise<void>` and takes `(connection, settings)`.
- Schema DDL is dumped by `packages/auth/scripts/gen-schema.ts` (getMigrations + compileMigrations against an empty sqlite) into `apps/api/migrations/0003_auth.sql`, then mirrored by `gen:migrations`. 13 tables, 21 indexes. Re-run both commands whenever better-auth or a plugin version bumps.
- The public `Auth` type is pinned to the core options instantiation: the fully plugin-instantiated type exceeds TypeScript's declaration-emit serialization limit. Plugin endpoints are exercised over HTTP in tests.

### Phase 2 — apps/webapp swap

- Replace `authkitMiddleware` with Better Auth cookie mount; keep the middleware order (locale → csrf → auth → guard) and the page-level guard semantics exactly.
- Re-implement `getAuthState` (server fn) on `auth.api.getSession`; `TopbarAuth` unchanged (same `{ configured, user }` shape).
- Keep the env gate: no D1/secret in an environment → signed-out rendering, auth routes unavailable. Previews stay browsable.
- Sign-in page: our own form (email/password + Google), design-system components, `{ en, th }` strings, `returnPathname` deep-link preservation preserved.
- Remove `@workos-inc/node` + `@workos/authkit-tanstack-react-start` from the app.

### Phase 3 — apps/api swap

- Delete `routes/auth.ts` (`biz_tok_` mock token layer) and the WorkOS dependency.
- Mount Better Auth (bearer + apiKey + oidcProvider) at `/api/v1/auth/*` and `/oauth2/*`; add apiKey capability scopes + audit fields per PRD §7.
- Middleware: resolve bearer/apiKey identity → `x-user-id` style context for `biz`/`plan`/`settings` routes (B-1 equivalent server-side).
- Update `auth.test.ts` / `app.test.ts`; golden tests for token issuance and scope enforcement.

### Phase 4 — apps/biz-mobile swap

## 5. Risks & mitigations

| Risk | Mitigation |
|---|---|
| We now own security patching | Pin better-auth version, dependabot, golden tests on auth routes, review gate on `packages/auth` changes |
| Two mounts share one DB | Same secret + same config factory from `packages/auth`; never configure per-app |
| D1 no interactive transactions | Better Auth Kysely/D1 documented path; our stores don't use transactions |
| Preview environments | Env gate preserved: no D1 binding/secret → signed-out rendering (today's behavior) |
| Email deliverability (verification) | WorkOS did it free; pick provider in Phase 1 or defer verification |
| User data loss in cutover | Pre-MLP: no real users expected; confirm before deprovisioning WorkOS |
